# Заметки для разработчика

Как устроен RenderSolver (до 0.6 — RenderCrashSolver), как его собирать и выпускать, что проверено и что нет. Описание для пользователей — в [README.md](README.md) и [README.txt](README.txt).

## Архитектура

Два процесса:

1. **`RenderSolver.exe`** (C#, WinForms) рендерит очередь сцен: по одной сцене за раз запускает Blender в фоне:
   ```
   blender.exe -b scene.blend --python-exit-code 2 -P resume_render.py -- [--output-dir DIR] [--prefix NAME] [--override-since TS] [--frames 1-100,120] [--info]
   ```
   Программа читает stdout/stderr Blender построчно, пишет весь вывод в лог-файл, а строки с префиксом `[resume_render] ` разбирает, чтобы обновлять прогресс и превью. По коду выхода решает, перезапускать ли Blender.

   **Очередь.** Каждая сцена — `Job`: файл, галочка «рендерить», свои кадры, другая папка вывода, Override. «Старт» помечает все сцены как ждущие и берёт первую отмеченную сверху (`RunNextJob`). Сцена заканчивается `FinishJob`: готово, ошибка (лимит попыток, код 2, неверные настройки) или стоп. После ошибки очередь идёт дальше, после «Стопа» — останавливается. Сцена, у которой по последнему чтению все кадры на диске, отмечается готовой без запуска Blender. Пока очередь идёт, можно добавлять сцены и менять ждущие; отредактированная готовая сцена снова становится ждущей. Заблокирована только сцена, которая рендерится.

   **Чтение сцен (`--info`)** идёт в фоне по одной сцене за раз и только пока очередь стоит, чтобы не держать в памяти две копии сцены. Изменение настроек сцены помечает её для перечитывания (с задержкой, чтобы не запускать Blender на каждую букву).

2. **`resume_render.py`** выполняется внутри Blender. Скрипт находит уже готовые кадры, ставит `frame_start` на первый недостающий, выключает `use_overwrite` (существующие кадры пропускаются, «дыры» в середине не приводят к повторному рендеру) и запускает `bpy.ops.render.render(animation=True)`.

   **Какие кадры нужны.** По умолчанию диапазон сцены с её шагом (`frame_step`; до 0.5 шаг игнорировался, и сцена с шагом 2 перезапускалась до лимита попыток). С `--frames` (в окне «Свои кадры») ровно перечисленные кадры: подряд идущие объединяются в отрезки, и каждый отрезок рендерится отдельным `render(animation=True)` начиная с первого недостающего кадра в нём. `STATUS` и `ALL_FRAMES_DONE` считаются по выбранным кадрам. Программа проверяет и нормализует список до запуска (`ParseFrames`), скрипт проверяет его ещё раз и при ошибке выходит с кодом 2.

| Файл | Что внутри |
|---|---|
| `RenderSolver.cs` | `Job` (сцена очереди), `Settings` (`settings.ini`), `MainForm`: интерфейс, очередь, запуск и перезапуск Blender, watchdog, разбор вывода, чтение сцен (`--info`), уведомления |
| `QueueList.cs` | Список очереди: отрисовка строк, выбор, галочка, перетаскивание строк, файлы и папки из проводника |
| `PreviewPanel.cs` | Просмотр готовых кадров: последний кадр, ползунок, флипбук |
| `Telegram.cs` | Bot API (`sendMessage`/`sendPhoto`/`getUpdates`) и окно настроек |
| `Theme.cs` | Тёмная тема: палитра, шрифты, самописные контролы (кнопки, поля, галочки, ползунок, плитки, цветной журнал), иконка, тёмный заголовок окна, прогресс на кнопке в панели задач |
| `resume_render.py` | Логика внутри Blender |

### Протокол строк `[resume_render]`

| Строка | Когда |
|---|---|
| `OUTPUT_EXT <ext>` | перед рендером |
| `OUTPUT_PATH <abs filepath>` | `scene.render.filepath` с учётом «Другой папки вывода», без расширения |
| `OUTPUT_DIR <dir>` | папка кадров |
| `STATUS total=N done=N missing=N` | итог сканирования папки (по выбранным кадрам) |
| `FRAME_START <frame>` | хендлер `render_pre` |
| `FRAME_DONE <frame> <seconds> <path>` | хендлер `render_write`; путь последним, в нём бывают пробелы |
| `RENDER_ERROR <message>` | рендер упал внутри Blender (обычно GPU/CUDA) |
| `ALL_FRAMES_DONE ...` | все кадры диапазона на диске: признак успешного завершения |
| `SCENE_PATH` / `SCENE_FRAMES <start> <end> <step>` / `SCENE_EXT` | только в режиме `--info`: программа узнаёт путь вывода и диапазон из сцены, ничего не рендеря (`<step>` добавлен в 0.5, программа читает и строку без него). `SCENE_PATH` — путь самой сцены, а `STATUS` в этом режиме с 0.6 считает кадры с учётом `--output-dir`/`--prefix` |
| `Rendering frames A-B` / `Rendering frame A` | перед каждым отрезком, если кадры выбраны несколькими отрезками |

### Коды выхода Blender

| Код | Значение | Что делает программа |
|---|---|---|
| 0 + `ALL_FRAMES_DONE` | готово | сцена готова, следующая сцена очереди |
| 0 без маркера | вышел, но не всё на диске | перезапуск |
| 2 | необработанное исключение в скрипте (`--python-exit-code 2`) | сцена — ошибка (повтор не поможет), очередь идёт дальше |
| 3 | `RENDER_ERROR`: скрипт поймал `RuntimeError` из `render()` и вышел через `os._exit(3)` | перезапуск как после краша |
| любой другой ≠ 0 | краш Blender (например, `0xC0000005`) | перезапуск |
| убит watchdog | нет нового кадра дольше таймаута | перезапуск |

Код 3 появился из-за ошибок CUDA `Illegal address`. После такой ошибки GPU-контекст сломан, и продолжать рендер в том же процессе нельзя, нужен новый Blender. Поэтому скрипт выходит через `os._exit`, а не продолжает работу.

### Две функции вывода (не путать)

| В интерфейсе | В коде / `settings.ini` | Аргумент скрипта | Что делает |
|---|---|---|---|
| «Другая папка вывода» | `CustomOutput`, `OutputDir`, `OutputPrefix` (до 0.3 ключ назывался `OverrideOutput`, он читается для совместимости) | `--output-dir`, `--prefix` | рендер в другую папку или с другим именем, `.blend` не меняется |
| «Override» | `Override`, `OverrideSince`, `OverrideKey` | `--override-since <unix-время>` | перерендер всех кадров |

Выбор кадров: «Свои кадры» = `CustomFrames`, `Frames` (текст как ввёл пользователь) → `--frames` (нормализованный, например `1-5,10,20-22`). С Override перерендериваются только выбранные кадры.

### `settings.ini`

Сверху общие ключи (Blender, логи, перезапуск, Telegram), дальше по секции `[job]` на сцену: `BlendFile`, `Enabled`, `CustomFrames`, `Frames`, `CustomOutput`, `OutputDir`, `OutputPrefix`, `Override`, `OverrideSince`, `OverrideKey`. Файл до 0.6 держал одну сцену в общих ключах (`BlendFile=` и т. д.): если секций `[job]` нет, эти ключи становятся первой сценой очереди, а при следующем сохранении файл переписывается в новом виде.

**Как устроен Override** (у каждой сцены свой). При первом «Старте» с галочкой программа запоминает время `OverrideSince` и ключ «сцена + путь вывода» (`OverrideKey`) и сохраняет их в `settings.ini`. При каждом запуске Blender в этой сессии скрипт получает `--override-since`:
- файлы кадров, сохранённые **раньше** этого времени, считаются устаревшими (не готовыми);
- файлы, сохранённые **позже**, относятся к текущему перерендеру и считаются готовыми;
- `use_overwrite` включён, чтобы устаревшие файлы перезаписывались.

Перерендер идёт по порядку, поэтому все кадры начиная с первого недостающего устаревшие или отсутствуют, и уже перерендеренное повторно не рендерится. После краша, «Стопа», закрытия программы или перезагрузки перерендер продолжается с места остановки, пока ключ совпадает.

Когда получен `ALL_FRAMES_DONE`, галочка снимается, а `OverrideSince` и `OverrideKey` очищаются. Ручное снятие галочки тоже очищает их, то есть отменяет перерендер.

Ограничение: время сравнивается с `mtime` файлов. Если папка вывода на сетевом диске с другими часами, возможны ошибки на величину рассинхрона.

## Сборка

Ничего ставить не нужно: используется `csc.exe` из .NET Framework 4, встроенного в Windows.

- **Только синтаксис C# 5:** без `$"..."`, `?.`, `=>`-членов, `nameof`. Компилятор старый.
- Исходники в **UTF-8 без BOM**, сборка с `/codepage:65001`: в строках интерфейса кириллица.
- **Масштаб экрана.** У главного окна и окна Telegram `AutoScaleMode.None`: размеры в пикселях задаются для 96 dpi и проходят через `Theme.S()` / `Theme.P()`, шрифты (в пунктах) масштабируются системой сами. Новые размеры пишите так же, иначе при 125–150% всё поедет. Скриншоты проверялись при 150%.
- `build.bat` — личная сборка с Telegram (`/define:TELEGRAM`), exe рядом с исходниками.
- `package.bat` — сборка для раздачи без Telegram: `dist\RenderSolver\` и `dist\RenderSolver_<VERSION>.zip`.
- Компилятор пишет временный файл рядом с exe: в папке с очень длинным путём (больше 260 символов) сборка падает с `CS1567`. Тогда соберите из копии в коротком пути.

Если захотите перейти на современный C# или .NET 8: проект маленький, переносится просто. Но тогда пользователям понадобится runtime или self-contained сборка, а сейчас это один exe примерно на 100 КБ без зависимостей.

## Выпуск версии

1. Поднять версию в `RenderSolver.cs` (`AppTitle`), `package.bat` (`VERSION`) и в первой строке `README.txt`.
2. Запустить `package.bat`.
3. Закоммитить, запушить и выложить релиз (тег на коммит с версией, отметка pre-release):
   ```
   gh release create v0.6 dist\RenderSolver_0.6.zip --prerelease --title "RenderSolver 0.6 (тест)"
   ```
   Без `gh`: Releases → Draft a new release на GitHub, тот же тег и zip.

## Тестирование без Blender

Удобно подсунуть вместо `blender.exe` маленькую консольную программу (или `.bat`), которая печатает строки протокола и выходит с нужным кодом: краш `-1073741819`, ошибка скрипта `2`, ошибка рендера `3`, успех `0` + `ALL_FRAMES_DONE`. Счётчик запусков в файле рядом со сценой позволяет имитировать «упал → перезапустился → дорендерил», а для очереди — чтобы падала только одна из сцен. Кадры (JPG через `System.Drawing`) лучше называть по имени сцены, чтобы сцены очереди не писали в одни и те же файлы. Подставной exe, пустые `.blend` и `settings.ini` с секциями `[job]` кладутся во временную папку вместе с программой и `resume_render.py`.

Проверить обработку ошибок в настоящем Blender без рендера:
```
blender -b --factory-startup --python-expr "import os; print('[resume_render] RENDER_ERROR test', flush=True); os._exit(3)"
```

## Что проверено, а что нет

Проверено:
- полный цикл на подставном Blender: краш → пауза → перезапуск → дорендер → «Готово»;
- превью кадров во время «рендера»;
- `--info`, обычный режим и проверка битых JPG на реальной сцене (1151 кадр) в Blender 4.3;
- выход с кодом 3 из настоящего Blender;
- Override на настоящем Blender (сцена из 4 кадров): перерендер с нуля, продолжение прерванного перерендера без повторного рендера уже готовых кадров, обычный режим после Override. В окне: подтверждение, перезапись, автоматическое снятие галочки;
- «Свои кадры» на Blender 5.2: `--info` и рендер с `--frames` (несколько отрезков, повторный запуск ничего не рендерит, дорендер недостающих), сцена с `frame_step=3`, неверный список (код 2), Override с выбранными кадрами (перезаписаны только они). В окне: «готово N из M выбранных», плитка кадров, подсказка и ошибка при неверном списке;
- «Другая папка вывода» через окно программы, в том числе путь с кириллицей и пробелами;
- запуск чистой распакованной сборки: автопоиск Blender, пути по умолчанию;
- тёмный интерфейс при 150% масштабе: на подставном Blender (рендер, краш → перезапуск, «Готово», лимит попыток, «Другая папка вывода», узкое окно 1040×640) и на настоящем Blender 5.2 (сцена из 5 кадров, превью PNG);
- Telegram: только с фальшивым токеном (HTTPS доходит, ошибки разбираются);
- очередь (0.6) на подставном Blender: 4 сцены, краш одной → перезапуск → дорендер, ошибка скрипта у другой → очередь идёт дальше, свои кадры у четвёртой, итог «готово 3 из 4, с ошибкой 1»; перенос старого `settings.ini` с одной сценой; добавление сцены через диалог, «Выше», вкладка «Настройки»;
- очередь на Blender 5.2: две сцены, у одной «Другая папка вывода» (кадры только в своей папке, «готово N из M» считается там же), у другой свои кадры `1-3, 20`.

Не проверено:
- перетаскивание строк мышью и файлов из проводника в список (код есть, автоматически не проверялось — только кнопками и диалогом);
- выбор нескольких файлов в диалоге «Добавить» (проверено на одном);
- перезапуск после **настоящего** краша и после настоящей ошибки CUDA на реальной машине;
- watchdog на реальном зависании;
- Telegram с настоящим ботом. Поэтому он скрыт в сборке для раздачи;
- превью EXR: System.Drawing его не читает, показывается сообщение;
- окно SmartScreen у пользователей (exe не подписан);
- прогресс на кнопке в панели задач и тёмные подсказки (tooltip) — не проверены глазами, только что код не падает;
- интерфейс при 100% и 125% масштабе.

## Известные проблемы и идеи

- **«Первый кадр ок, второй падает с CUDA Illegal address»** — из лога тестера, Blender 4.4. С 0.2 программа перезапускает Blender, но каждый запуск заново грузит сцену. Варианты:
  - режим «один кадр на процесс»;
  - автоматически выключать `scene.render.use_persistent_data` в скрипте (опцией).
- **Чтение сцены (`--info`) идёт с аддонами пользователя.** С BlenderKit, Rokoko и т. п. оно занимает ~16 с вместо пары секунд. Можно запускать `--info` с `--factory-startup`: путь вывода и диапазон кадров от аддонов не зависят (сам рендер оставить с аддонами).
- **Watchdog с фиксированным таймаутом** (60 мин по умолчанию). Лучше адаптивный: N × среднее время кадра, но не меньше X минут.
- **Telegram:** доделать и проверить с реальным ботом. Токен хранится в `settings.ini` открытым текстом.
- Интерфейс только на русском.
- Нет цифровой подписи: SmartScreen и антивирусы ругаются.
- Очередь: свой Blender для каждой сцены (сейчас один на всех), выбор камеры / слоя рендера, общая оценка времени всей очереди.
- Логи Blender огромные (миллионы строк в день). Можно фильтровать шум перед записью в файл или включить ротацию.
